# Диспетчер проверок UPPAAL

Диспетчер запускает формулы последовательно, сохраняет каждую попытку и показывает
время, CPU, текущую/пиковую память и последние Throughput/Load, если UPPAAL их выдаёт.
Процент готовности и время до завершения не вычисляются: размер пространства неизвестен.

Нужен Python >= 3.10 с установленным этим пакетом, либо `PYTHONPATH=src` из checkout.
Дополнительных зависимостей диспетчер не добавляет. Запускайте **Windows Python для
Windows verifyta.exe**, Linux Python для Linux verifyta. Вызов Windows verifier
через Linux Python/WSL запрещён: его PID не даёт достоверных native-метрик.

## Быстрый запуск (PowerShell)

```powershell
$env:PYTHONPATH = "$PWD\src"
python -m uppaal_mcp.verification_manager init C:\uppaal-runs\c02-001 `
  --model C:\models\model.xml --queries C:\models\C02.q `
  --verifyta 'C:\Program Files (x86)\UPPAAL-5.0.0\bin\verifyta.exe' `
  --timeout 86400 --memory-mib 8192
python -m uppaal_mcp.verification_manager start C:\uppaal-runs\c02-001
```

Храните очередь на локальном диске Windows, например `C:\uppaal-runs`,
а не на `\\wsl.localhost`/UNC: там OS-блокировка может не поддерживаться.
Исходный код и входные модели можно читать из WSL.

`init` только создаёт очередь, ничего не проверяет. Каталог должен быть новым.
Время задаётся **на формулу**, память — в МиБ; по умолчанию 600 секунд и 2048 МиБ.
Пример с сутками не запускается автоматически. `.q` содержит одну формулу на строку;
пустые строки и отдельные строки комментариев обрабатываются существующим parser.
Сложные многострочные запросы предварительно приводите к одной строке.

`start` работает на переднем плане: оставьте терминал открытым. В другом терминале:

```powershell
python -m uppaal_mcp.verification_manager status C:\uppaal-runs\c02-001
python -m uppaal_mcp.verification_manager pause C:\uppaal-runs\c02-001
python -m uppaal_mcp.verification_manager resume C:\uppaal-runs\c02-001
python -m uppaal_mcp.verification_manager stop C:\uppaal-runs\c02-001
```

- `pause`: текущая формула продолжает работать; следующая ждёт. Память текущего
  процесса не освобождается. Это **пауза очереди**, а не заморозка процесса.
- `resume`: разрешить дальнейшие задания уже работающему диспетчеру.
- `stop` или Ctrl+C в рабочем терминале: завершить и дождаться текущего процесса,
  сохранить логи и результат `stopped`. Опрос обычно раз в секунду; preflight
  версии ограничен 20 секундами и не прерывается командой stop мгновенно.
- После выхода диспетчера: `python -m uppaal_mcp.verification_manager continue <каталог>`.
  Пропускаются только формулы с результатом success/satisfied или success/violated.
  Timeout/error/inconclusive/stopped повторяются **с начала формулы**, отдельной
  попыткой. Внутреннее пространство поиска verifyta не сохраняется.

Один каталог защищён OS-блокировкой от двух рабочих процессов. После аварии
незавершённая попытка сохраняется; при известном ещё живом PID продолжение
отклоняется: сначала проверьте процесс в диспетчере задач. Старые PID не убиваются
автоматически, поскольку PID мог быть переиспользован. При аварии в узком окне
между запуском дочернего процесса и сохранением PID возможен неучтённый дочерний
процесс: перед восстановлением после принудительного убийства менеджера проверьте
оставшиеся процессы verifyta. Для штатного завершения используйте `stop`.

## Артефакты и результаты

- `queue.json`, `model.xml`, исходный `.q` и отдельные `query-NNN.q`: снимок входов,
  SHA256 модели/запросов/verifier, параметры. Оригиналы могут меняться независимо.
  Изменение снимка или исполняемого файла отклоняется при продолжении. Для другой
  модели, параметров или инструмента создавайте новую очередь.
- `status.json`: атомарный последний статус; команда status добавляет проверку
  `worker_active`. Старый phase=running без живого worker не означает работающий поиск.
- `sessions/<id>/`: фактическая версия, raw stdout/stderr preflight, окружение,
  hash кода диспетчера и конфигурации очереди.
- `attempts/<id>/`: команда, PID, timestamps, verdict/status, hashes, stdout/stderr,
  диагностические XML-трассы, `telemetry.csv` и контрольные суммы файлов.

CPU — накопленные секунды процесса. На Windows память — WorkingSet/PeakWorkingSet,
на Linux — RSS/VmHWM, а не общий расход системы или private bytes. Порог памяти
проверяется дискретно, это не жёсткий лимит аллокации. Нет метрики — `null`, а не
выдуманный ноль. Если метрика памяти недоступна у живого процесса, попытка завершается
как monitor_error. Очень короткий процесс может завершиться без измерения памяти.
Процент выполненных **формул** можно получить из completed/total; это не процент
исследованных состояний. CSV подходит для последующего построения графиков.

Проверки идут с BFS и некоторой диагностической трассой (`-o 0 -t 0`). Рабочий
каталог verifier — каталог его executable. Глобальные переменные окружения и
лицензия не меняются. Произвольные shell-команды не выполняются.

Timeout и memory_limit сохраняются, после них очередь переходит к следующей
формуле. Error/monitor_error/stop останавливают очередь. Выход 0 означает, что все
формулы имеют окончательные результаты, **в том числе отрицательные**. Выход 2 —
незавершённая очередь или ошибка; смотрите verdict каждой формулы.

Существующий parser отвергает ненулевой exit code, ошибки и неполные результаты,
даже если до ошибки напечатано satisfied. Версия/preflight не является verification.
Для научного evidence дополните пакет принятым baseline, parameter set, instance
vector и решением независимого reviewer. Диспетчер сам не закрывает C02/P3.
