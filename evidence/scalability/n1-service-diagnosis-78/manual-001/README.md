# N=1: ручная трасса после автоматических таймаутов

Дополнение к диагностике [Issue #78](https://github.com/artmus208/uppaal_sdn_isac/issues/78).
Цель — понять, соответствует ли вручную найденный путь вопросу, на который
автоматические проверки не успели ответить, и сохранить воспроизводимые входы.

## Предпосылки

В серии P4 (#76/#77) было **90 запусков для N=1–4 с повторами**:
72 завершились таймаутом, 18 — с verdict. Из этих 18 результатов 12 — satisfied,
6 — violated: автоматический проверяющий обнаружил возможность переполнения
очереди. Это не «72 неудачных попытки пройти один сценарий» и не 18 доказательств
того, что вся модель корректна.

Для исходной цели N=1 `E<> family_grant_0` найдены пять исторических попыток:
DFS 30 с, random DFS 30 с и три DFS по 60 с. Все — timeout без verdict/trace.
Позднее три разных промежуточных/уточнённых запроса D1–D3 с BFS по 30 с также
закончились таймаутом. Лимит времени исчерпан; это не отрицательный verdict.

## Что сделано и что показывают трассы

Пользователь вручную выбрал переходы в UPPAAL и сохранил три контрольные трассы.
Полная [папка отладки](UPPAAL-debug-N1) содержит 19 исходных файлов; копии сверены
побайтно, hashes — в [inventory](debug-folder-inventory.json). PNG/JPG в папке
не было. Названия промежуточных XTR — пользовательские подписи контрольных точек;
автоматический разбор этого дополнения выполнен для финальной XTR.

В финальной трассе разобраны **69 состояний**. Их значения совпадают с
предикатами D1 (SelectMode), D2 (готовность к обслуживанию) и D3 (grant в Publish_0
без overflow). В последнем состоянии grant=1, очередь изменилась 1→0,
arrival=0, mode=JOINT; overflow_seen=0 во всех сохранённых состояниях. Время 10
показано на пользовательском скриншоте при открытии трассы на исходном XML.

Это **симуляция плюс статический разбор её файла**, не новый verdict verifyta:
аудит не перепроверяет допустимость всех timed-переходов и не декодирует DBM.
GUI XML отличается от baseline дополнительной изолированной локацией; точные
hashes и результаты структурного сравнения сохранены. Загрузка XTR на baseline
не объявляется независимой полной валидацией пути.

Grant здесь означает **абстрактное обслуживание очереди**. В конце APP-запрос
ещё pending, admission_loss=1 и PHY-команда pending. Поэтому доставка пакета,
завершение услуги, ACK и SLA этой трассой не установлены. Наличие пути без
переполнения совместимо с другими путями, где переполнение найдено автоматически.

## Почему автоматический поиск не успел

Подтверждённая причина остановки — временной лимит, а не лимит памяти.
Пять исходных service-попыток N=1 потребляли примерно 168–238 MiB при пороге 2 GiB.
Точная причина затрат времени не измерена: в service-логах нет итогового
счётчика состояний. У одного перехода SharedLoad есть **2592 варианта входа**;
это установленный источник ветвления. Автоматический поиск рассматривает
альтернативы, тогда как пользователь выбирал один путь. Вклад перебора,
обработки зон и сжатия требует отдельного эксперимента; «взрыв состояний» здесь
не выдаётся за доказанный профиль производительности.

## Предложения для тестирования и манифеста

Это рекомендации для отдельного решения владельцев процессов, **не изменение
манифеста, модели, acceptance criteria или результатов предыдущих запусков**.

1. В отчётах всегда разделять `execution_status` и `property_verdict`, показывать
   satisfied/violated/timeout отдельно. Контракт v2 уже требует этого — следует
   проверить применение в сводках, а не вводить новое значение success.
2. Перед большой серией проводить ограниченную диагностику N=1 по цепочке
   «вход → очередь → выбор режима → grant → команда/ACK → APP outcome».
   Для каждого звена заранее определить формулу и смысл. Такая подготовка
   дополняет, но не заменяет запланированные измерения масштабируемости.
3. Разделять «выбор обслуживающего», «абстрактное снятие из очереди» и
   «успешную услугу» в названиях query/claim. Если статье нужна доставка или
   SLA, определить соответствующие события и обосновать их связь с grant;
   усиление guard или изменение модели требует отдельной задачи и baseline.
4. Сохранять simulation checkpoints с model hash, версией GUI/engine и
   описанием выбранных входов. Проверять дрейф XML после сохранения в редакторе.
   Для повторного использования свидетельства нужна независимая проверка пути;
   выбор последней строки импортированной XTR её не заменяет.
5. Для таймаутов заранее сохранять доступные метрики прогресса, время фаз,
   CPU/RAM и настройки. Отсутствующий счётчик помечать `not_available`.
   Повторы для оценки затрат не считать независимым расширением покрытия:
   одинаковый детерминированный поиск начинается заново.
6. Следующий эксперимент менять по одной настройке и ограничивать бюджет.
   Подготовлен один исходный service-query с plain DBM вместо compact DBM
   (60 с, 2 GiB, весь протокол 180 с, без повторов). Он **не запущен** и требует
   отдельного согласования. Рост лимита или смена представления не гарантируют
   успеха. Контролируемое сравнение требует одинакового хоста и условий.

Для §2/§3.1/§3.3 манифеста v2 полезен пример этого случая: timeout ≠ violated,
simulation ≠ automatic verdict, grant ≠ APP completion. Основные правила уже
есть в v2; возможное изменение — пример и операционный checklist для будущих
Issues/runner summaries. Правки `manifests/` здесь не выполнялись.
