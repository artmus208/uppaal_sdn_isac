## Рекомендация

Для проверки именно границы очереди рекомендую конечную абстракцию заполнения
с отдельным состоянием превышения. Пакеты, FIFO, байты и новые retry/admission
политики не нужны. Это рекомендуемое расширение модели, а не пассивный recorder.
Решение о его включении принимает Reviewer/Integrator; этот PR его не подменяет.

Существующие классы сами по себе не дают требуемого свойства. Нельзя получить
границу заполнения простым добавлением запроса к текущему XML. Если расширение
не принимается, очередь в C01 остаётся непокрытой; реакция на Q_CRIT и single-slot
bridges не являются заменой. Изменение самого требования — отдельная governance
диспозиция, а не незаметная правка смысла C01.

## Почему текущего представления недостаточно

На pinned base:
- mac/generator.py:246–249 задаёт QueueClass_t и отдельный BufferClass_t.
- integrated/boundary.py:85–92 выбирает queueClass и bufferClass независимо
  на каждом MAC tick. Между выборками нет баланса поступления/обслуживания.
- mac/generator.py:317–324: A_Q реагирует на класс; QueueDraining не меняет
  заполнение и не свидетельствует об обслуженном элементе.
- integrated/boundary.py:111–125 и mac/generator.py:310–312: schedule/ACK —
  управление PHY; ACK не является событием удаления данных из очереди.
- mac/alpha.py перечисляет исключённые raw queue/buffer samples, но не задаёт
  отображение q,K -> queueClass.

Поэтому одна и та же наблюдаемая последовательность классов совместима как
с q<=K, так и с q>K: связь с q вообще отсутствует. Запрос, видящий только эти
классы, не различит эти интерпретации. Это аргумент недостаточности текущего
контракта, не доказательство невозможности любой конечной классовой абстракции.
Для её обоснования всё равно понадобятся связь с ёмкостью и правила переходов.
Q_CRIT нельзя без принятого определения объявить полным или переполненным.

## Предлагаемая семантика (вся таблица требует принятия)

Объект: одна агрегированная очередь коммуникационной нагрузки MAC в текущей
single-UAV композиции. Отдельный A_BUF и транспортные bridges не включаются
в её ёмкость; отсутствие переполнения всех буферов сети не заявляется.

| Элемент | Предложение |
|---|---|
| Единица | Абстрактная единица работы, не пакет и не физический объём |
| Параметры | K — ёмкость; 0 < L < M < H <= K — границы классов |
| Состояние | q в 0..K+1; K+1 означает «превышение было достигнуто», терминальное для учёта очереди |
| Начало | q=0, overflow_seen=false |
| Период | Существующий bus_T_mac_tick; новую физическую скорость не вводить |
| Поступление | a в {0,1}: новая абстрактная работа, принятая в очередь на этом tick |
| Обслуживание | s в {0,1}, s<=q; s=1 разрешено только при SCH_COMM или SCH_JOINT |
| Порядок | Сначала завершение старой работы, затем поступление: next=q-s+a |
| Превышение | При next>K: q=K+1, overflow_seen=true; переход не запрещать |
| После превышения | q и overflow_seen сохраняются; остальные процессы продолжают работу |
| Отбрасывание | d=0: новый drop/admission механизм не вводится; resource_reject не считается удалением данных |

SCH_CONSTRAINED намеренно не даёт service credit: на текущих входах нет
доказательства обслуживания коммуникационной очереди в этом режиме. Даже при
SCH_COMM/SCH_JOINT возможен s=0; ACK не гарантирует s=1. Это консервативная
предлагаемая среда, а не извлечённый из исходников факт. Смысл a — принятое
поступление непосредственно в MAC, независимо от отложенного APP/SDN admission #36.

Оба события выполняются одним обновлением существующего MAC load tick в
Boundary_E_MAC_LOAD; q имеет одного writer. Пропуск последующего mac_mac_tick
не отменяет уже состоявшееся обновление нагрузки. Service credit относится
к scheduleMode до обновления нагрузки. Дополнительных ACK receivers нет.

Классификация: q=0 -> Q_EMPTY; 1..L -> Q_LOW; L+1..M -> Q_MED;
M+1..H-1 -> Q_HIGH; H..K+1 -> Q_CRIT. Для непустого Q_HIGH требуется M+1<H.
При выборе параметров проверять 0<L<M<H<=K и M+1<H.
Классы buffer/delay/drop/resource остаются отдельными входами: связность с
физической очередью ими не доказана. Особенно B_OVERFLOW != (q>K).

Числа K,L,M,H здесь не назначены: текущие входы их не обосновывают.
Для исполнения нужен явно принятый абстрактный parameter tuple; это не требует
выдавать его за физическую калибровку. Без tuple реализацию не активировать.

## Что именно проверять

Будущий основной запрос: A[] !mac_queue_overflow_seen.
Эквивалентная граница для предложенного latch: A[] mac_queue_q <= mac_queue_K.
Новые symbols пока не существуют; это спецификация, не готовый query pack.

Тип 0..K+1 оставляет место нарушению. Нельзя заменить его на 0..K,
насыщать счётчик на K или запрещать поступление при q=K ради успеха проверки.
До первого превышения баланс точный в абстрактных единицах. После превышения
сохраняется только нарушение: последующие длины/восстановление не моделируются.
Поэтому такой latch пригоден для safety, но не для drain-time/throughput claims.

При a=1 и s=0 на последовательных tick превышение возможно. Поэтому
положительный результат не обещается. Если композиция допускает такой путь,
P3 должен сохранить отрицательный результат и trace. Нельзя добавлять fairness,
обязательное обслуживание или ограничивать arrivals после получения trace.
Необходимость таких условий означала бы новое научное решение.

## Проверки будущей реализации

1. q=0, s=0, a=0 сохраняет ноль; обслуживание пустой очереди недоступно.
2. q=K-1, s=0, a=1 даёт K без нарушения.
3. q=K, s=0, a=1 даёт K+1 и sticky violation; отрицательный контроль обязан
   опровергнуть safety. Никакого integer range error или блокировки перехода.
4. q=K, s=1, a=1 остаётся K; порядок событий явно фиксирован.
5. ACK, QueueDraining и resource_reject сами по себе q не уменьшают.
6. После превышения нарушение сохраняется при любых дальнейших ticks.
7. Классы на 0,L,L+1,M,M+1,H-1,H,K,K+1 соответствуют таблице.
8. Достижимость непустой очереди/full/overflow проверяется отдельно от safety;
   недостижимость tick не считается содержательным доказательством ёмкости.

## Влияние и следующий шаг

Учёт добавляет K+2 значений q и sticky bit (bit определяется q на достижимых
состояниях), без нового clock. Это оценка дискретного фактора, не число explored
states. Производный queueClass убирает независимый выбор класса и меняет
множество поведений: расширение нельзя объявлять пассивным или эквивалентным.
Сохранение прежних контрпримеров/свойств автоматически не предполагается.

Для независимой приёмки достаточно одного решения: принять либо отклонить
предложенную семантику и, при принятии, записать K,L,M,H.
Если требуется другая service/drop семантика, исправить этот контракт до кода.

После принятия — отдельный implementation Issue с предлагаемыми путями:
- src/uppaal_mcp/integrated/boundary.py
- src/uppaal_mcp/integrated/generator.py
- tests/test_integrated_queue_contract.py
- evidence/instantiation/<implementation-issue>-queue-contract/**

generator.py включён для metadata/version/provenance новой семантики.
Этот список не резервирует scope. Перед активацией нужны освобождение
пересекающихся #19/#35 scopes, свежий base и проверка source pinning.
Если pinning требует другого пути, сначала расширить implementation Issue.
