# Минимальный контракт C01/C02

Issue #39. Автор: vadimnbkg. Статус: предложение для независимого принятия P2.
Base: `aeeb62d4893db7f4bfd7d4243932860c50132f66`, branch `read`.
Это спецификация и candidate queries, не verification и не принятие Gate 1.
Политики, генераторы, параметры, XML и manifests не изменяются.

## Решение с наименьшим вмешательством

1. Сохранить существующую функциональную модель и принятые #31/#38.
2. Использовать существующую запись MAC ACK для проверки elapsed safety.
3. Специфицировать пассивный счётчик recovery dispatch; не добавлять retry policy.
4. Не подменять очередь MAC однослотовым мостом или диапазоном enum.
5. Не вводить произвольные K, arrivals/service или физические единицы ради
   положительного результата. Численная граница очереди пока не покрыта.

## C01 — deadlock

Область — вся интегрированная композиция. Запрос `A[] not deadlock` остаётся
обязательным, даже если известные дефекты могут дать отрицательный результат.
Это не проверка отсутствия бесконечных zero-time циклов. PHY measurement 5/6,
SDN rule/control waits и влияние оставленных observers не исключаются из модели.
Отрицательный результат P3 требует trace; он не является поводом задним числом
сужать набор проверок. До Gate 1 положительный результат P3 не требуется.

## C01 — границы очередей: реальный пробел

`levels_tex/MAC_resource_scheduling_formalization.tex`, раздел «Автоматы очереди
и буфера», задаёт реакцию на Q_CRIT/B_OVERFLOW, а не динамику заполнения.
`src/uppaal_mcp/mac/alpha.py` не содержит численного отображения длины очереди
в классы. `Boundary_E_MAC_LOAD` в `integrated/boundary.py` выбирает классы
недетерминированно. Спецификация #17 явно исключает вывод ёмкости из классов.

Следовательно, на текущих входах нельзя вывести ни K, ни предикат q<=K.
Проверки `queueClass<=Q_CRIT`, реакции на критический класс или отсутствия
B_OVERFLOW не выдаются за проверку численной границы очереди. B_OVERFLOW —
отдельный класс буфера, его эквивалентность переполнению очереди не установлена.

Сравнение вариантов:

| Вариант | Изменение | Условие допустимости |
|---|---|---|
| Существующая абстракция + обоснование | Только контракт/queries | Нужна сохраняющая нарушение связь с ограниченной очередью; сейчас отсутствует |
| Абстрактное заполнение без пакетов | Конечное дополнительное состояние | Принятые K, admission/service/drop events и связь с MAC; сейчас не заданы |
| Только single-slot bridges | Контракт/queries, возможно recorder | Отдельное принятие более узкого смысла C01; не покрывает MAC queue автоматически |

Выбор: сначала получить недостающий queue abstraction contract; автоматического
перехода к изменению модели нет. Если нельзя обосновать существующую абстракцию,
минимальное расширение — баланс заполнения без объектов-пакетов. Вместимость
может быть явно абстрактным параметром, не обязательно физически калиброванным,
но её значение и события должны быть приняты P2. Насыщение счётчика на K без
фиксации превышения делает safety-проверку бессодержательной.

## C01 — recovery attempts

Эпизод начинается на принятом A_REC link_failure/node_failure в StableConfig,
заканчивается локальным success/failure того же эпизода. Offer среды не начало.
Попытка — фактическая отправка одного из:

- `bus_rec_policy_request!` — основная standby попытка;
- `bus_rec_flow_request!` — основная reembedding попытка;
- `bus_rollback_request!` — rollback.

За эпизод проверять primary<=1, rollback<=1, total<=2. Прямой rollback считается
одной отправкой; локальный failure до dispatch — нулём. ACK и failure_report
не являются попытками. Один внешний fault не подменяет этот счёт.

Минимальная будущая реализация: recorder только на существующих A_REC edges.
primary/rollback имеют диапазон 0..2, где 2 — насыщаемое превышение предела 1;
total имеет 0..3, где 3 — превышение предела 2. Sticky violation сохраняется
между эпизодами. Reset только на реальном новом эпизоде, sticky не сбрасывать.
Повторный start при active и dispatch без active также записывают ошибку.
Ни guards, ни invariants, ни synchronizations не зависят от recorder.
Нельзя ограничить домен допустимым пределом и блокировать нарушающий переход.

Этот recorder ещё не реализован; соответствующий query не объявляется готовым.
Проверка его реализации должна включать искусственную третью отправку и
сравнение функциональных переходов до/после удаления monitoring updates.

## C02 — MAC send-to-ACK-or-timeout <=3

Использовать принятый контракт #31: начало — фактическая отправка MAC мосту,
конец — matching ACK либо ScheduleFailure. ACK не означает успешный сервис.
RequestReady/ApplySchedule до отправки не входят в этот интервал.

`candidates.q` разделяет:
- sticky late и active-age safety непосредственно по recorder;
- безусловный leads-to как самостоятельный диагностический запрос завершения;
- достижимость начала и timeout для обнаружения vacuity. Успешный ACK нужно
  подтвердить trace перехода WaitPHYAck->Idle либо отдельным event marker:
  достижимость Idle сама по себе бессодержательна, поскольку это initial state.

Успех leads-to нельзя предполагать; при zero-time циклах он может быть false.
Комментарий об условии time divergence не меняет семантику UPPAAL-запроса.
Для условного bounded completion на time-divergent трассах требуется отдельно
принятая аргументация: active age не сбрасывается между start/end, отсутствие
просрочки запрещает активному эпизоду пережить deadline, а все его завершения
соответствуют разрешённым исходам. P3 проверяет предпосылки и reachability;
безусловное завершение на Zeno-трассах этим не заявляется. Нельзя исключить
поведения модели добавлением scheduler/fairness-автомата без отдельной приёмки.

## Приёмка и воспроизведение

Матрица покрытия: deadlock — query готов, результата нет; очередь — blocked on
abstraction contract; attempts — recorder specified, not implemented; ACK safety
и diagnostics — candidates, not verified; условный completion — требует принятия
семантики и последующей проверки предпосылок. C01/C02 не закрыты.

Адресное решение независимого P2 reviewer: принять определения attempts/ACK,
а для очереди выбрать и обосновать одно из трёх представлений выше. Это конкретный
остаток, не просьба повторно принимать все контракты. После необходимых scoped
изменений — принятие P1/P2 и governance freeze. #36 остаётся deferred.
