# Декомпозиция рецензий по доказательным результатам — v1

Формат статьи пока вынесен за рамки. План строится не по рецензентам, а по независимым доказательным результатам. Операционные роли, ветки, write scopes и handoff-контракты определяет `manifests/collaboration-v1.yaml`; этот документ определяет научную декомпозицию и критерии целостности.

## 1. Формальная постановка

Пусть \(R=\{r_1,\dots,r_n\}\) — атомарные замечания из всех трёх рецензий.

Для каждого замечания фиксируется кортеж:

\[
r_i=(comment\_id,\ source\_refs,\ problem,\ artifact,\ evidence,\ acceptance,\ dependencies).
\]

`comment_id` — стабильный идентификатор атомарного требования. Повторяющиеся формулировки разных рецензентов перечисляются в `source_refs`, но не создают новые задачи.

Два замечания считаются дублями только тогда, когда совпадают:

\[
artifact_i=artifact_j
\land evidence_i=evidence_j
\land acceptance_i=acceptance_j.
\]

Для каждого замечания должен существовать ровно один основной исполнитель:

\[
\forall r_i\in R:\quad \exists! owner(r_i).
\]

Другие процессы могут предоставлять зависимости, но не должны независимо решать то же замечание.

Классификация относительно центральной верификации:

- `CORE` — результат получается непосредственно запуском UPPAAL.
- `RELATED` — влияет на конфигурацию, размер пространства состояний или интерпретацию verification results, но имеет собственный критерий готовности.
- `INDEPENDENT` — может быть принято рецензентом без знания результатов model checking.
- `DEFERRED` — сознательно отложено, но не потеряно.

## 2. Дедуплицированная структура замечаний

### CORE — центральное ядро

Это объединённое замечание reviewers 2 и 3:

- `C01` — выполнить structural correctness checks:
   - отсутствие deadlock;
   - границы очередей;
   - границы числа recovery attempts.
- `C02` — выполнить хотя бы одну bounded-response проверку.
- `C03` — представить реальные результаты model checking.
- `C04` — для нарушенных свойств показать counterexample или диагностический trace.
- `C05` — зафиксировать для каждого запуска:
   - версию UPPAAL;
   - конфигурацию модели;
   - количество экземпляров;
   - время;
   - пиковую память;
   - оборудование.
- `C06` — сделать вывод о практической проверяемости и state explosion.

Это один владелец требований, а не шесть независимых задач. `C01–C05` проверяются на одной frozen baseline-конфигурации; вывод `C06` объединяет этот результат с серией `P4`, где source/generator baseline неизменна, а `instance_vector` и сгенерированный `model_hash` меняются контролируемо.

### RELATED — связанные, но не являющиеся дублями

- `R01` — определить число экземпляров автоматов для base stations, devices, UAV и других агентов.
- `R02` — описать правила построения multi-agent-композиции.
- `R03` — исследовать масштабируемость при увеличении числа экземпляров.
- `R04` — сопоставить экспериментальную границу с ограничениями из работы Глониной.
- `R05` — подробно разобрать один автомат.
- `R06` — объяснить, как его абстракция ограничивает число состояний и переходов.
- `R07` — связать сквозной сценарий `PHY → MAC → SDN/RIC → SLA` с конкретным verification run.

Один успешный verification run маленькой конфигурации не закрывает эти замечания.

### INDEPENDENT-MAJOR — отдельная валидация

Эту ветку нельзя смешивать с verification:

- `validation`: адекватно ли автоматы изображают реальную сеть;
- `verification`: выполняются ли свойства внутри уже принятой формальной модели.

Сюда входят:

- `V01` — методика проверки адекватности автоматов и их композиции.
- `V02` — обоснование порогов `GOOD/WEAK/OUTAGE`, `FRESH/STALE`.
- `V03` — обоснование типичных значений дедлайнов.
- `V04` — связь UPPAAL с NS-3, OMNeT++ или внешними данными.
- `V05` — источник каждого существенного параметра модели.

### INDEPENDENT — уникальные самостоятельные требования

- `I01` — литература по timed-automata моделям сетевых протоколов.
- `I02` — перспективные probabilistic/priced extensions и statistical model checking.
- `I03` — читаемые, обрезанные и увеличенные рисунки.
- `I04` — удаление курсора, углов окон и прочего мусора.
- `I05` — размещение рисунков рядом с соответствующим текстом.
- `I06` — языковая вычитка и исправление склеенных слов.

### DEFERRED

- `D01` — выбор IEEE/LNCS и окончательное форматирование.

## 3. Параллельные процессы

| Процесс | Класс | Ответственность | Выходной артефакт | Зависимости |
|---|---|---|---|---|
| `P0 Baseline` | Координация | Зафиксировать исходники статьи и модели; принять Gate 1 | Baseline manifest + gate record | Нет |
| `P1 Validation` | Independent-major | Пороги, дедлайны, адекватность модели, связь с симуляторами | Validation report + parameter table | `P0: candidate` |
| `P2 Instantiation` | Related | Число агентов, композиция, детальный автомат и абстракция | Model-scope specification | `P0: candidate` |
| `P3 Verification` | Core | Проверка свойств на frozen-модели | Verification evidence bundle | `P1`, `P2`, Gate 1 |
| `P4 Scalability` | Related | Серия запусков при росте числа экземпляров; сопоставление с Глониной | Scalability/resource report | `P1`, `P2`, Gate 1 |
| `P5 Scenarios` | Related | Сквозные PHY–SLA сценарии, привязанные к машинным результатам | Scenario traces | Черновик: `P1`, `P2`; приёмка: `P3`, Gate 1 |
| `P6 Literature` | Independent | Сетевые timed automata и статистические расширения | Literature notes + BibTeX | `P0: candidate` |
| `P7 Figures` | Independent | Читаемость, очистка и размещение рисунков | Figure bundle + placement map | Предварительно `P0: candidate`, финально Gate 1 |
| `P9a Integration draft` | Координация | Свести доказательные артефакты в один черновик | Integrated manuscript draft + response matrix | `P1–P7` |
| `P8 Language` | Independent | Языковая и терминологическая вычитка интегрированного черновика | Editorial patch | `P9a` |
| `P9b Final assembly` | Координация | Применить редактуру и провести финальную сверку | Unified manuscript + final response matrix | `P8`, `P9a` |

Первичное владение атомарными требованиями:

| `comment_id` | Единственный owner | Evidence dependencies |
|---|---|---|
| `C01–C06` | `P3` | `P1`, `P2`; для границы масштабирования — данные `P4` |
| `V01–V05` | `P1` | `P0: candidate` |
| `R01`, `R02`, `R05`, `R06` | `P2` | `P0: candidate` |
| `R03`, `R04` | `P4` | `P1`, `P2`, Gate 1 |
| `R07` | `P5` | `P1`, `P2`, принятый run из `P3` |
| `I01`, `I02` | `P6` | `P0: candidate` |
| `I03–I05` | `P7` | Gate 1 для финальных изображений |
| `I06` | `P8` | `P9a` |
| `D01` | `P9b` при активации | Отложено отдельным решением |

## 4. Контракты процессов

### P0 — Baseline

Выход:

```text
baseline_id
source_commit
manuscript_source
manuscript_hash
model_sources
source_hashes
generator_hash
toolchain
parameter_set
instance_vector
query_set
status
gate_1_record
```

`hardware_description` не является свойством baseline: оно фиксируется в каждом `run record`, потому что разные процессы могут запускаться на разных машинах.

У `P0` два состояния: `candidate` открывает подготовительную работу `P1/P2/P6/P7`, а `frozen` достигается только после принятия Gate 1. Это не циклическая зависимость: `P1` и `P2` используют candidate baseline и возвращают данные, необходимые для его заморозки.

Gate 1 принимает координатор `P0`. Чек-лист Gate 1:

- канонический исходник статьи и его hash записаны;
- source/generator hashes модели записаны;
- композиция, `parameter_set`, `instance_vector` и query IDs однозначны;
- версия UPPAAL/verifyta и параметры запуска записаны;
- статическая валидация baseline проходит;
- доступ к рабочему verifyta runner и лицензии подтверждён;
- пересекающихся write scopes между активными процессами нет;
- решение принято отдельной записью с commit SHA, временем и владельцем.

Критерий готовности: любой участник может воспроизвести одну и ту же конфигурацию, а Gate 1 имеет явную запись `accepted`.

Эквивалентность `samplepaper.tex` и рассмотренного PDF не предполагается автоматически и не опровергается одной текстовой выборкой. В baseline отдельно фиксируются канонический исходник, статус его сборки и результат сравнения с PDF. Выбор IEEE/LNCS для этого не требуется.

### P1 — Validation

Выход:

- таблица всех порогов и дедлайнов;
- источник каждого значения;
- метод сопоставления поведения автомата и сети;
- схема обмена данными с NS-3/OMNeT++;
- отдельно перечисленные validation claims.

Критерий готовности: ни один существенный параметр не объясняется словами «выбран разумно» без источника или метода калибровки.

### P2 — Instantiation and abstraction

Выход:

- перечень типов автоматов;
- количество экземпляров каждого типа;
- правила их синхронизации;
- переменные, влияющие на state space;
- подробный разбор одного автомата;
- объяснение влияния выбранной абстракции на число состояний и переходов.

Критерий готовности: по спецификации можно однозначно построить тестовую конфигурацию модели.

### P3 — Core verification

Выход для каждого query:

```text
property_id
formal_query
query_hash
source_commit
source_hash
generator_hash
model_hash
parameter_set
instance_vector
result
runtime
peak_memory
states_explored
counterexample_reference
run_id
host_id
hardware_description
os
UPPAAL_version
verifyta_options
```

Минимальный набор:

- три structural properties;
- одна bounded-response property;
- reachability значимых состояний;
- counterexample для каждого отрицательного результата.

Критерий готовности: ни одного утверждения «property verified» без машинного результата и `run_id`.

Координатор `P0` владеет схемой run record, `P3` — индексом core verification bundle, а `P4` — собственной веткой `scalability` внутри evidence bundle. Процессы не перезаписывают результаты друг друга и связывают их только через `run_id`.

### P4 — Scalability

P3 отвечает: «проверяется ли baseline-конфигурация?»

P4 отвечает: «как вычислительная стоимость меняется с числом агентов?»

Выход:

- несколько возрастающих конфигураций;
- время и память для каждой;
- максимальная успешно проверенная конфигурация;
- первая конфигурация с timeout/OOM/state explosion;
- `source_hash` и `generator_hash`, общие с baseline;
- отдельные `model_hash`, `instance_vector`, `run_id` и описание оборудования для каждой конфигурации;
- сопоставление наблюдаемой границы с ограничениями из работы Глониной;
- ограничения применимости выводов.

Критерий готовности: наличие экспериментальной границы проверяемости, а не общего утверждения «модель масштабируема».

### P5 — End-to-end scenarios

Для каждого сценария:

```text
initial_state
PHY_event
PHY_classification
MAC_decision
SDN_policy
application_outcome
SLA_property
verification_run_id
```

Критерий готовности: читатель может проследить причинную цепочку без реконструкции логики по четырём разделам статьи.

Черновик причинной цепочки можно подготовить после `P1` и `P2`, но сценарий не принимается без существующего `verification_run_id` из `P3`. Поэтому `P5` относится к `RELATED`, а не к независимым процессам.

### P6 — Literature

Два независимых результата:

- existing timed-automata models of network protocols — для Introduction;
- probabilistic/priced/statistical extensions — для Discussion/Future Work.

Работа Глониной принадлежит только `P4`, чтобы один источник не получил двух независимых интерпретаций.

### P7 — Figures

Единый пакет закрывает пересекающиеся визуальные замечания, но сохраняет разные критерии:

- текст читается в конечном масштабе статьи;
- показаны релевантные states, guards и channels;
- отсутствуют курсоры и элементы интерфейса;
- подпись соответствует модели из manifest;
- рисунок расположен рядом с соответствующим разделом.

### P8 — Language

Выполняется после `P9a`:

- устранить merged words;
- сократить перегруженные предложения;
- вычитать Introduction и Cross-Layer Operational Semantics;
- проверить единообразие `validation`, `verification`, `simulation`, `experiment`.

Выход — отдельный editorial patch и список терминологических решений. `P8` не редактирует канонический manuscript напрямую.

### P9a/P9b — Integration

`P9a` строит первый общий черновик только из принятых артефактов `P1–P7` и создаёт response matrix:

```text
comment_id
source_refs
owner
artifact
evidence_reference
manuscript_section
status
```

`P9b` применяет patch из `P8`, повторно проверяет hashes и ссылки на evidence, затем выпускает единую статью и окончательную response matrix. Между `P9a` и `P9b` другие процессы не меняют `samplepaper.tex`.

## 5. Порядок выполнения

```text
P0: фиксация исходников
 │
 ├── P1: validation/calibration ──┐
 ├── P2: instances/abstraction ───┤
 ├── P6: literature               │
 └── P7: предварительная графика  │
                                  │
                         Gate 1 (owner: P0)
                         Frozen model baseline
                                  │
                     ┌────────────┴────────────┐
                     │                         │
               P3 Verification           P4 Scalability
                     │                         │
               P5 Scenario final              │
                     └────────────┬────────────┘
                                  │
                         P7 Final figures
                                  │
                    P9a Integration draft
                                  │
                         P8 Final editing
                                  │
                     P9b Final assembly
```

`P3` и `P4` выполняются параллельно на общей frozen source/generator baseline, но используют разные конфигурации, `model_hash` и `run_id`. Черновик `P5` может идти параллельно с ними; его финальная доказательная привязка ждёт `P3`.

## 6. Правила обратной сборки

Чтобы независимые процессы не создали несколько несовместимых статей:

1. Только `P9a` и `P9b` редактируют итоговый `levels_tex/samplepaper.tex`.
2. Остальные процессы возвращают артефакты и готовые фрагменты, но не переписывают общие разделы.
3. `P8` возвращает editorial patch; применяет его только `P9b`.
4. Все числа берутся из одного индексированного evidence bundle.
5. Все эксперименты ссылаются на общие `source_hash` и `generator_hash`; `model_hash` фиксируется отдельно для каждой сгенерированной конфигурации.
6. Каждый `comment_id` в review matrix имеет одного владельца, а все исходные формулировки сохраняются в `source_refs`.
7. `Validation` и `verification` всегда оформляются отдельными подразделами.
8. Сквозные сценарии используют ровно тот `parameter_set` и `instance_vector`, на который указывает их `verification_run_id`.
9. Выводы ограничиваются реально проверенными конфигурациями.

## 7. Финальные критерии целостности

Работа считается собранной, если:

- каждый `comment_id` имеет статус `addressed`, `deferred` или аргументированное `not adopted`;
- reviewers 2 и 3 получают один согласованный блок реальных verification results;
- вычислительные параметры совпадают во всех таблицах и тексте;
- масштабируемость не выводится из одного запуска;
- validation не выдаётся за verification;
- рисунки соответствуют проверенной версии XML;
- в abstract больше не говорится, что работа лишь «intended for verification», если результаты действительно добавлены;
- существует таблица `comment_id/source_refs → процесс → артефакт → раздел статьи → доказательство выполнения`.

Это и есть минимальная архитектура параллельной работы без дублирования и с контролируемой интеграцией.
