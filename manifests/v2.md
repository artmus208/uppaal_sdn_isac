# Научный манифест v2: утверждения, доказательства и завершение исследования

Статус: **proposal / not active**. Подготовлено в рамках
[Issue #62](https://github.com/artmus208/uppaal_sdn_isac/issues/62).
Публикация или merge этого предложения сами по себе не активируют v2.
До отдельного решения действуют [v1.md](v1.md),
[collaboration-v1.yaml](collaboration-v1.yaml), [AGENTS.md](../AGENTS.md)
и [CONTRIBUTING.md](../CONTRIBUTING.md).
[Карта перехода](v2-migration.md) сохраняет все 25 ID и их владельцев.

## 1. Цель и границы

Цель — завершить текущую статью о формальной модели SDN/ISAC с воспроизводимыми
результатами и точной областью каждого вывода. Сохраняются требования рецензентов,
декомпозиция P0–P7, P8, P9a/P9b и ранее принятые решения в их исходной области.
Обобщённая модель произвольной сети, доказательство детерминизма всей композиции,
новая физическая калибровка или внедрение SMC не становятся дополнительными
обязанностями только из-за появления этого манифеста.

Каждый вывод относится к явно указанному объекту: одной конфигурации, семейству
конфигураций или реальной системе при обоснованной связи с моделью. Эти области
не взаимозаменяемы. Корректность модели относительно формальной спецификации
и адекватность описания реальной сети требуют разных оснований.

Отрицательный результат полезен для исследования, но не означает выполнения
свойства. Полный отчёт о незавершённой проверке также не закрывает требование
автоматически. Сужение обещания статьи, отсрочка обязательства или замена
предписанного способа доказательства требуют явного решения reviewer/integrator.

### 1.1. Решения при неполной информации

Инженерные решения принимаются при ограниченной осведомлённости и неполной
информации. Обоснованный компромисс допустим: фиксируются его причины,
рассмотренные альтернативы, ограничения и последствия. Предпосылки решения
и подтверждённые гарантии указываются раздельно.

Неопределённость допустима. Если утверждение не удалось ни доказать, ни
опровергнуть в выбранных условиях и бюджете, оно остаётся открытым. Это само
по себе не запрещает продолжать работу в явно определённой области, где
дальнейшие выводы обоснованы независимо от истинности открытого утверждения.
Необходимость, глубина и приоритет дальнейшей проверки определяются
последствиями ошибки и целями исследования.

Для открытого вопроса достаточно краткой записи в существующем Issue или
документе: что проверено, в какой области и бюджете, какие зависимости затронуты
и при каких условиях следует вернуться к проверке. Уже сохранённые сведения
используются по ссылке; отдельный отчёт на каждый вопрос не требуется.
Возврат целесообразен, когда новая информация или изменившиеся условия могут
повлиять на вывод либо дальнейшая проверка имеет обоснованный ожидаемый вклад
в результат исследования.

Обязательные зависимости и gates сохраняются. Если открытый вопрос блокирует
обязательный результат, изменение требования, области claim или зависимости
оформляется явным решением reviewer/integrator. Открытое утверждение при этом
не становится доказанным или опровергнутым.

## 2. Evidence и статусы

Для результата раздельно фиксируются следующие признаки. Их можно хранить
в сопроводительном индексе со ссылкой на существующую запись; изменять формат
исторических run records для этого не требуется.

| Поле | Смысл |
|---|---|
| `evidence_kind` | Способ получения основания из таблицы ниже. |
| `execution_status` | Исходный статус выполнения инструмента; для чистого математического аргумента — `not_applicable`. |
| `property_verdict` | Явный результат конкретной формулы, как его сообщил инструмент; отсутствие результата и `not_applicable` различаются. |
| `claim_scope` | Модель, предпосылки и область, в которой допустим вывод. |
| `evidence_availability` | Какие исходники, stdout/stderr, trace и ресурсы реально доступны; пробелы перечисляются. |
| `acceptance_status` | Решение reviewer/integrator со ссылкой; не выводится из exit code, наличия PR или этой таблицы. |

| `evidence_kind` | Допустимый смысл и необходимое основание |
|---|---|
| `direct_model_checking` | Результат конкретного query на конкретной полной, локальной или reduced model. Тип модели указан явно; результат reduced model ещё не относится к полной композиции. |
| `mathematical_argument` | Явное утверждение, предпосылки, доказательство и идентифицируемые исходники. Скрипт поиска шаблона в XML может поддерживать аргумент, но не заменяет его проверку по существу. |
| `reduction_with_transfer` | Проверка сокращённой модели вместе с обоснованием переноса конкретного класса свойств на исходную. Нужны обе модели, отношение между ними и область переноса. |
| `simulation` | Поведение в выполненных прогонах. Универсальный вывод допустим лишь при отдельном доказательстве достаточности этих прогонов для данного свойства. |
| `external_validation` | Сопоставление с внешними данными, реализацией или симулятором по заранее указанным величинам и критериям; совпадение с другим симулятором само по себе не доказывает физическую адекватность. |
| `static_validation` | Проверка синтаксиса, структуры, параметров или согласованности artifacts. Не устанавливает поведенческое свойство. |

Для model checking сохраняется прежний минимальный контракт: `run_id`, исходный
`status`, явный verdict конкретного query, `model_hash`, `query_hash` и точная
`tool_version`. Воспроизводимость требует также commit, параметров, instance
vector, полной команды, operating environment, hardware и путей к
stdout/stderr/trace. Изменённый XML получает собственный `model_hash`.

Успешное выполнение и отрицательный verdict — разрешённый отрицательный результат.
`timeout`, `error`, `oom`/лимит памяти и отсутствие verdict не устанавливают
истинность или ложность свойства. Машинный claim требует `status=success` и явного verdict конкретного query.
Самостоятельные успешные per-query runs внутри серии учитываются отдельно.
Частичный stdout общего аварийного/прерванного run остаётся диагностикой;
для принимаемого результата нужен отдельный успешный run по принятому контракту. Отсутствующая метрика обозначается как
неизвестная, а не нулём. Сохраняется исходное написание статусов инструмента.

Принятый математический аргумент не становится машинным verdict. Metadata-only
запись не становится полным воспроизводимым bundle: отсутствие raw artifacts
остаётся видимым даже при наличии прежнего решения о приёмке.

## 3. Контракт утверждения

Для существенного утверждения используется следующий минимальный контракт.
Существующие документы можно связать ссылками; дублировать их содержание
или создавать пустой artifact для каждого поля не требуется. Неприменимость
поля объясняется явно.

```text
comment_id, source_refs, primary_owner
claim_id, statement, property_class, formal_query_or_theorem
scope: baseline/source/model/query-or-statement identifiers,
       parameters, instance vector or family, time units and horizon
environment assumptions, component-contract dependencies
roles: production components, environment, observers, test harness
evidence kind, proof/reduction inputs, transfer argument if needed
non-vacuity and progress checks
artifact references, availability gaps, limitations
review/disposition reference, permitted manuscript claim
```

### 3.1. Смысл свойства и композиции

Для bounded response указываются события начала и конца, сбросы часов, единицы,
допустимые timeout/rollback исходы и предпосылки прогресса. Условие time divergence
или fairness пишется явно; оно не означает, что любая конечная трасса имеет
нужное продолжение. Для очередей различаются ёмкость, число поступлений,
обслуживание и утверждение о переполнении.

Условие, предполагаемое компонентом, должно быть обеспечено окружением или
явно принято как внешняя предпосылка. Взаимные обещания двух компонентов без
обоснования композиции не образуют доказательство. ACK управляющей команды,
обслуживание очереди и восстановление SLA — разные события; связь между ними
требует собственного аргумента или trace.

### 3.2. Редукции, observers и harness

Перенос результата задаёт отношение исходной и сокращённой моделей, проекцию
наблюдений, направление вывода и класс сохраняемых свойств. Сохранение safety
не означает автоматически сохранения deadlock freedom, liveness, времени ответа
или существования сценария. Проверка малого числа экземпляров не является
общим cutoff без доказательства его условий для данной композиции.

Для каждого вспомогательного автомата фиксируется роль: пассивное наблюдение,
активное тестовое окружение или намеренное ограничение поведения. Требования
зависят от этой роли. Для error observer обосновывается, что он обнаруживает
нарушение, а не блокирует его; для активного harness — какие входы он допускает
и какую область проверяет. Удаление query не удаляет observer из модели.
Negative control помогает обнаружить ошибку постановки, но не заменяет
обоснование корректности observer или переноса.

### 3.3. Невакуумность и бюджет проверки

Для условного свойства проверяется достижимость запускающего события; для
протокола — возможность существенных шагов, а не только стартовой конфигурации.
Проверки невакуумности имеют собственные формулы и ограничения. Они не
подменяют доказательство основного свойства или прогресса всей системы.

До дорогого запуска записываются научный вопрос, фиксированные inputs, бюджет
и условие остановки. Повтор запуска объясняется изменением бюджета, метода
или входов. Исчерпание бюджета — результат эксперимента; выбор другой редукции,
доказательства или более узкого claim не меняет критерии приёмки молча.
После исчерпания бюджета применяется правило §1.1: вопрос фиксируется как
открытый, а независимая работа продолжается. Новый запуск получает обоснование
ожидаемого вклада в выводы исследования.

## 4. Процессы и результаты

Primary ownership атомарных требований сохраняется. Эта таблица задаёт научный
результат; разрешённые пути и текущие назначения по-прежнему задают Issues.

| Процесс | Требования | Результат и уточнение |
|---|---|---|
| P0 Baseline | Coordination-only | Candidate/frozen baseline, gate records и governance decisions; подготовка baseline не равна его приёмке. |
| P1 Validation | V01–V05 | Методика адекватности, источники параметров, единицы и область validation. Выполненное внешнее сопоставление отделяется от плана такого сопоставления. |
| P2 Instantiation | R01, R02, R05, R06 | Экземпляры, интерфейсы композиции, детальный автомат, абстракция и допустимые конфигурации; assumptions/guarantees компонентов. |
| P3 Verification | C01–C06 | Индекс утверждений и evidence: прямые verdicts, proof/transfer, отрицательные результаты и незавершённые проверки различимы. C06 зависит от P4. |
| P4 Scalability | R03, R04 | Воспроизводимая серия роста экземпляров, ресурсы, наблюдаемая граница и сопоставление с ограничениями работы Глониной. |
| P5 Scenarios | R07 | Причинная цепочка PHY → MAC → SDN/RIC → SLA со ссылкой на принятый verification run и явными границами интерпретации. |
| P6 Literature | I01, I02 | Сетевые timed automata, вероятностные/стоимостные расширения и SMC как литература и перспектива. |
| P7 Figures | I03–I05 | Figure bundle и placement map; финальные рисунки привязаны к принятой модели. |
| P9a Integration draft | Integration | Принятые результаты P1–P7, рукопись и response matrix с допустимой формулировкой каждого вывода. |
| P8 Language | I06 | Отдельный editorial patch интегрированного текста; научные ограничения сохраняются. |
| P9b Final assembly | Final assembly; D01 условно | Применение принятого patch, финальная сверка и сборка. D01 остаётся deferred до отдельной активации. |

Для P3 сохраняются три structural correctness обязательства C01, хотя бы одна
bounded-response проверка, реальные model-checking результаты, диагностика
нарушений и полный контракт запусков C02–C05. Замена требуемого машинного
результата математическим аргументом или сужение исходного обязательства
допустимы только в явно принятой disposition; этот манифест её не создаёт.
Рукопись `levels_tex/samplepaper.tex` изменяют только P9a/P9b.

### 4.1. Осуществимость серии P4

До ресурсной серии P2 и P4 согласуют семейство: изменяемую размерность,
instance vectors, интерфейсы, хранение состояния по сущностям и арбитраж.
Воспроизводимая генерация минимум двух размеров и статическая проверка их
контрактов показывают осуществимость серии, но не закрывают R03 и не являются
verification. Отдельно фиксируются вопросы, которым нужны поведенческие проверки.

P2 отвечает за правила композиции/необходимые изменения модели; P4 — за план
и измерения; P0 — за baseline decision. Новый процесс не вводится. Подготовка
семейства не должна ждать P3_complete, иначе возникает цикл с C06.

Внутри серии фиксируются source/generator baseline и согласованная схема свойств;
каждый экземпляр получает собственные XML, hashes, параметры и run records.
Вариация параметров, vectors и подстановка в queries допустимы только в пределах
принятого семейства. Выход за его границы или изменение смысла queries требуют
отдельного baseline/Gate 1 decision.
Изменение семантики или generator требует согласованного scope и нового baseline
с Gate 1. Старый baseline сохраняется. Использование старого P3 вместе с новой
серией требует принятого обоснования соответствия; без него evidence P3 для
новой базы получают заново. Сравнение разных baselines явно маркируется и не
выдаётся за предусмотренную v1 серию на общей source/generator baseline.

В отчёте разделяются затраты генерации, simulation, model checking и прочего
анализа. Для ресурсов сохраняются query, стратегия, hardware, время, память,
лимиты и исход каждого запуска. R03 требует серии роста и наблюдаемой границы
практической проверяемости. Если бюджет исчерпан до её установления, сообщается
измеренная область и требуется отдельная disposition; автоматического закрытия
R03/C06 не происходит. Один timeout не устанавливает универсальную границу.

P4 сохраняет первичное владение сравнением с Глониной. P1/P2/P3 используют
его разбор предпосылок по ссылке, не создавая конкурирующих результатов R04.
Сопоставляются класс систем, спецификация, метод, конфигурации и метрики.
Стоимость MCSSimCpp simulation нельзя выдавать за стоимость exhaustive UPPAAL
model checking, а cutoff из другой композиции — за границу нашей сети.

## 5. Зависимости и gates

```text
P0 candidate → подготовка P1, P2, P6, предварительного P7
принятые P1/P2 → Gate 1: точный frozen baseline
Gate 1 → P3 core; P4 (при готовом семействе); финальный P7
P1/P2 → черновик P5
P3_core_evidence_accepted + Gate 1 → финальная приёмка P5
принятый P4 → C06 → P3_complete
принятые требуемые P1–P7 → P9a → P8
Gate 2 + принятый P8 patch → P9b → integration PR read → main
```

`P3_core_evidence_accepted` относится к C01–C05 и открывает финальную приёмку P5.
`P3_complete` включает также C06 после P4. Наличие полного evidence bundle
не равнозначно любому из этих решений. Временная отсрочка deadlock, отрицательный
queue verdict или открытый PR не становятся waiver через изменение манифеста.

Для P5 принятый run соответствует модели, параметрам и instance vector сценария.
Reduced witness либо отдельный ACK не заменяет сквозной сценарий; связь с полной
композицией и конечным SLA результатом обосновывается отдельно.

Gate 1 фиксирует модель, generator, query set, параметры, instance vector,
commit/hashes и tool version после P1/P2; он не означает истинности всех свойств.
Gate 2 требует принятых результатов P3/P4/P5 и согласованности всех численных
утверждений, ограничений и dispositions с artifacts. Машинный вывод имеет
traceability до run/query; математический — до точного утверждения и proof.

Gate принимает назначенный reviewer/integrator, не автор результата. Проверка
вспомогательным агентом автора полезна для качества, но не является независимой
приёмкой. Наличие commit, PR, merge или успешного CI само по себе gate не закрывает.

## 6. Интеграция и критерий завершения статьи

Response matrix связывает исходный ID и source_refs с единственным owner,
контрактом утверждения, artifacts/evidence, местом в рукописи, ограничениями
и решением reviewer/integrator. `addressed`, `deferred`, `not adopted` — разные
исходы disposition, не verdict формулы. Новая отсрочка требует явного решения.

При P9a/P9b проверяются:

- Соответствие формулировок точной конфигурации, семейству и предпосылкам.
- Разделение положительных, отрицательных, незавершённых и недоступных результатов.
- Отсутствие подмены abstract time физическим временем, ACK — SLA, simulation — verification.
- Собственная серия масштабирования и честное сопоставление с внешней работой.
- Читаемость рисунков, единицы и traceability численных утверждений.
- Явная disposition всех исходных требований; новые исследовательские обещания
  не добавляются без отдельного решения о scope.

Методические основания уточнений: [исходная статья](../pdfs/018100004273.pdf)
и [диссертация Глониной](../pdfs/dissertation.pdf), печатные стр. 23–25, 62–86
(спецификация, эквивалентность и локальная проверка; стр. 82–86 —
детерминированность относительно временной диаграммы), 88–95
(инструментальная реализация и simulation), 98–116, 244–245 (эксперименты), 139–209 (условия параметрических
редукций). Эти результаты служат образцом постановки доказательства;
их применимость к нашей модели сама требует обоснования.

Активация производится отдельным governance deliverable по
[карте перехода](v2-migration.md). Этот пакет не меняет действующие указатели,
исторические inputs, принятый baseline, статусы Issues или научную приёмку.
