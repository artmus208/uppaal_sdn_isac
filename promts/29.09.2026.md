Научный вопрос:
как растёт стоимость формальной проверки при увеличении числа взаимодействующих UAV-контекстов с одним общим ресурсом обслуживания MAC-очередей?

Сохраняй семантику PR #67:
- отдельные PHY/MAC/SDN/APP-контексты каждого UAV;
- один общий ресурс: не более одной возможности обслуживания за MAC-эпоху;
- обслуживание необязательно, fairness и приоритеты не добавляются;
- SDN-контексты — логические агенты отдельных UAV, а не модель производительности централизованного контроллера;
- прежние ограничения наблюдателей и абстракции сохраняются.

Что сделать:

1. Расширить генератор на N=1,2,3,4.
   Одна команда должна воспроизводить все четыре размера, параметры, instance vectors и hashes. Используй существующий прототип. Для N=1,2 сравни XML и queries с PR #67; ожидается сохранение прежнего поведения, любое отличие явно объясни. Не заявляй эквивалентность по одному структурному сравнению.

2. Проверить композицию.
   Для каждого размера проверь изоляцию состояния и часов, адресацию каналов, состав экземпляров, общий ресурс и корректность маршрутизации событий. Сохрани содержательные отрицательные проверки на смешение сущностей и нарушение общей ёмкости. Проверь воспроизводимость из чистого checkout и загрузку всех четырёх моделей в UPPAAL.

3. Подготовить компактный протокол P4.
   Выбери минимальный набор формул, позволяющий получить содержательное сравнение:
   - ограничение общего ресурса обслуживания;
   - достижимость обслуживания каждой сущности и совместного backlog;
   - выбранное свойство из исходных обязательств с точным сохранением смысла.

   Для каждой формулы укажи научный смысл, роль в эксперименте, область утверждения, способ подстановки N, необходимые предпосылки и проверку невакуозности. Различай стоимость проверки одной сущности и всей совокупности: увеличение числа queries не должно незаметно подменять рост стоимости одного query.

   Зафиксируй стратегию поиска, параметры, порядок запусков, повторы, лимиты времени/памяти и stop condition. Выбор ресурсов обоснуй доступным оборудованием. Раздели затраты генерации, компиляции и model checking.

4. Выполнить только короткие проверки поведения.
   Для этой задачи разрешены последовательные диагностические запуски:
   - до 60 секунд на отдельный запуск;
   - порог остановки по измеряемой памяти 2 ГиБ;
   - общий бюджет работы verifier до 20 минут;

   Это подготовительные проверки, не полная ресурсная серия P4. E<> true подтверждает лишь загрузку модели. Timeout и ошибка не устанавливают истинность свойства. Если корректно измерять память невозможно, не запускай проверку с фиктивным ограничением.
